# Room migrations

The database has been at version 3 since PR #40, with a hand-written `Migration` for each step.
What was missing was any way to know whether those migrations work. This is how that gap was
closed and what it costs to keep closed.

## What was there before

Two migrations, and nothing that ran them.

`AppDatabase` declares `exportSchema = true`, and `data/build.gradle.kts` has named a schema
directory since PR #36:

```kotlin
room {
    schemaDirectory("$projectDir/schemas")
}
```

So Room's compiler has been writing `data/schemas/…/<version>.json` on every build for months.
Nobody ever committed one. The directory was not ignored — it was simply never added, which is
the quieter version of the same problem: the build produced the artifact, the artifact went
into a working tree, and CI threw the working tree away at the end of the job.

That left `MIGRATION_1_2` and `MIGRATION_2_3` as prose. Both are careful, both are commented
with the reasoning behind every default, and neither had ever been executed. A migration that
has never run is not a migration; it is a plan for one. The specific failure it hides is the
worst kind Room has, because it does not happen on the developer's machine: a fresh install
creates the schema from the entities and is always correct, so the only user who sees a broken
migration is one who had the previous version installed.

## Exported schemas

`data/schemas/com.kojo.boilerplate.core.database.AppDatabase/{1,2,3}.json` are now committed.
They are Room's own output, not a transcription: versions 1 and 2 were regenerated by building
the commits that declared them (`5aa38e0` and `b723ff2`), because Room's compiler only ever
exports the version of the code in front of it.

Two things keep them honest:

- **`Room schemas are committed`**, a CI step that runs straight after `compileDebugKotlin` and
  fails on an untracked or modified file under `data/schemas`. `git diff` alone is not enough —
  a brand-new version's file is untracked, and untracked files are exactly what `git diff` does
  not report. Both halves are checked.
- **The migration suite reads them.** They are not documentation sitting beside the code; they
  are the input the tests start from, so a missing file fails the build rather than degrading
  quietly.

## The migration suite

`data/src/test/kotlin/…/migration/AppDatabaseMigrationTest.kt`.

### Why it is a unit test

The canonical home for this is `androidTest` with `androidx.room.testing.MigrationTestHelper`.
Nothing in `androidTest` runs in this repository. There is no emulator in CI — putting one there
is Phase 12's own spec item — so `UserDaoTest` has never executed, and a migration suite written
the same way would have joined it. Robolectric gives `src/test` a real SQLite implementation and
a real `Context`, so this suite runs under `testDebugUnitTest`, which CI already gates on.

`MigrationTestHelper` is not used for the same reason: it loads its schema bundles through an
*instrumentation* context's assets. `ExportedSchema` reads the same files off disk instead —
about forty lines, no assets plumbing, and no dependency on a source set that never runs.

### What actually validates a migration

Room does. Every test opens the real `AppDatabase` rather than inspecting the upgraded file:

```kotlin
Room.databaseBuilder(context, AppDatabase::class.java, DATABASE_NAME)
    .addMigrations(*migrations)
    .build()
    .openHelper
    .writableDatabase          // ← the assertion
```

`RoomOpenHelper.onUpgrade` runs the migrations and then compares the result against the schema
compiled into `AppDatabase_Impl`, throwing on any difference. Reaching the next line is the
proof that the migration lands where the entities say it should.

`everyExportedVersionMigratesToTheCurrentSchema` is a second, independent check: it migrates
from every exported version and compares the result, table by table and column by column,
against a database created fresh at the current version. That covers what Room's own validator
does not look at — column defaults, and indices Room did not declare — and it grows on its own
as versions are added, because the versions come from the directory listing rather than from a
list in the test.

### Two things the comparison deliberately does not do

- **It does not compare `sqlite_master.sql`.** `ALTER TABLE … ADD COLUMN` appends to the
  statement the table was *originally* created with, so an upgraded `users` carries the
  version-1 text and a fresh one carries whatever Room generates today. The two databases are
  identical to SQLite and differ in most bytes of that string.
- **It sorts columns by name.** Reordering the properties of an `@Entity` changes the order a
  fresh install creates them in and cannot change the order an upgraded database already has.
  Room's own `TableInfo` comparison ignores column order, so comparing it here would fail on a
  difference Room accepts.

## Adding a version

1. Change the entities and bump `version` in `@Database`.
2. Add a `Migration` for the new step in `AppDatabase.Companion` and register it wherever the
   database is built — `DatabaseModule` for the app, `migrations` in the test for the suite.
3. Build. Room writes the new `data/schemas/…/<version>.json`; commit it in the same change.
4. `everyVersionStepHasAMigration` and `exportedSchemasAreContiguousAndReachTheCurrentVersion`
   fail if either step 2 or step 3 is skipped, so neither can be forgotten quietly.

## What is still not covered

- **Auto-migrations.** None are declared; every step here is hand-written, which is the right
  default while the schema changes are small enough to read.
- **Anything that needs a device.** Robolectric's SQLite is the real library, but it is the
  host's build of it. A behaviour that differs between an OEM's SQLite and the host's would not
  show up here — that is what Phase 12's emulator matrix is for.
- **Downgrades.** `fallbackToDestructiveMigrationOnDowngrade` is not set and no downgrade path
  exists, so installing an older build over a newer database throws. That is the correct
  behaviour for a boilerplate and is called out here rather than left to be discovered.
