# R8: full mode, keep rules, and the mapping file

R8 is the only part of this build whose configuration cannot fail. A misspelled Gradle property
fails at configuration time; a wrong dependency version fails at resolution; a keep rule that
matches nothing produces a green build, a smaller APK, and a crash the first time something in it
reflects. R8 emits no warning for a `-keep` whose pattern names no class, because a pattern that
matches nothing is legal and often deliberate — it is how one configuration file covers several
build flavours.

Everything below follows from that. The rules are few and each one is written down with the
runtime failure it prevents; the ones that libraries already ship are deliberately *not* here;
and a script checks the survivors against the shrunk output so a rule going quiet is a red build
rather than a field report.

## Full mode

`android.enableR8.fullMode=true` in `gradle.properties`. This is AGP 8's default and it is written
down anyway, for two reasons: it is the flag somebody flips to `false` to make a crash go away,
and it changes what the rules below have to cover, so a build that switched modes silently would
change which of them are load-bearing.

Four differences matter here:

| Full mode | What it breaks without a rule |
|---|---|
| Generic signatures and annotations are stripped from classes that are not kept | Anything reading a type argument at runtime — Retrofit's `Call<Foo>`, a `suspend` function's `Continuation` |
| An interface with no visible implementation is assumed to have none, and calls through it are replaced with `null` | Retrofit service interfaces, which only ever have a `Proxy` implementation |
| Default constructors are not kept for classes only instantiated reflectively | Anything built by `Class.newInstance` |
| `-keep` no longer implies "and do not optimise" as widely | Objects whose only reader is a reflective lookup |

Retrofit's own `META-INF/proguard/retrofit2.pro` covers the first three for its own surface, which
is most of the exposure in this app.

## Which rules are ours

Almost none, and that is the point. An AAR's `consumer-rules.pro` and a JAR's
`META-INF/proguard/*.pro` are merged into the configuration R8 runs with, so Retrofit, OkHttp,
Room, Hilt, kotlinx.serialization, WorkManager, CameraX, ML Kit and Play Integrity all arrive with
their own rules and need nothing in `app/proguard-rules.pro`. Copying a rule out of a library's
README when the library already ships it is how that file grows: a duplicate can never fail, so it
is never removed, and the next reader cannot tell which lines are holding something up.

`build/outputs/mapping/minified/configuration.txt` is the merged set R8 actually used. That, not a
library's documentation, is what to read when deciding whether a rule is already covered.

What is left is three rules and one attribute pair.

### Serializable objects the app declares

```
-keepclassmembers @kotlinx.serialization.Serializable class com.kojo.boilerplate.** {
    public static ** INSTANCE;
    kotlinx.serialization.KSerializer serializer(...);
}
```

A library rule cannot name our packages, so this half is always the app's. The types at risk are
the serializable **objects**: `AppDestination.SignIn` and its three siblings are `data object`s,
and nothing in the app ever writes `SignIn.INSTANCE` — Navigation resolves a typed route through
`serializer()` at runtime. In full mode R8 therefore sees a static field with no reader and an
object with no instantiation site. The conditional rule kotlinx.serialization 1.7.3 ships
(`-if @Serializable class ** { public static ** INSTANCE; }`) does not hold it up; the fix for
exactly that case went upstream in 1.8.0 as an unconditional `-keepclassmembers`
([kotlinx.serialization#2861](https://github.com/Kotlin/kotlinx.serialization/issues/2861),
[b/379996140](https://issuetracker.google.com/issues/379996140)). This rule is that one, scoped to
this app, and it can be deleted when `serialization` in `gradle/libs.versions.toml` reaches 1.8.0.

Scoped to `com.kojo.boilerplate.**` rather than to a sub-package deliberately. The serializable
types live in two packages in two different Gradle modules today — `core.navigation` for the
routes, `core.network.model` for the DTOs — and the rule this replaced broke precisely by naming a
path and then being left behind when the code moved.

### Generated protobuf fields

```
-keepclassmembers class * extends com.google.protobuf.GeneratedMessageLite {
    <fields>;
}
```

`protobuf-javalite` is a plain JAR with no `META-INF/proguard` entry, so unlike every other
dependency here it ships no rules and this one is ours.

Lite generated code has no per-field methods for the runtime to call. A `GeneratedMessageLite`
describes its own layout with a `RawMessageInfo` — a packed string naming each field — and
`MessageSchema` resolves those names against the class with `getDeclaredField` the first time a
message is parsed or serialised. Rename the fields and the lookup throws; remove them and there is
nothing to look up. Either way the first symptom is on the start-up path, where the preferences
store is read before the first frame.

Fields only: every generated method is called directly from `UserPreferencesSerializer` and the
DataStore flows, so tree shaking keeps what is reachable and stays free to rename and inline the
rest.

### Line numbers, and the file names that go with them

```
-keepattributes SourceFile,LineNumberTable
-renamesourcefileattribute SourceFile
```

Without the first, a retraced stack trace names the class and the method but not the line, which
is most of what a stack trace is for. The second then removes the original `.kt` names from the
shipped artifact, because the retrace side reads them from the mapping instead.

### What was removed

`-keepnames @dagger.hilt.android.lifecycle.HiltViewModel class * extends ViewModel` was in this
file and is not any more. It dates from the Hilt that looked a view model up by name: the
generated module bound each one into a map with `@StringKey("com.kojo…HomeViewModel")` and
`HiltViewModelFactory` matched that against `modelClass.getName()`, so renaming the class produced
`Cannot create an instance of class …` on navigation. Hilt 2.57.2 does not work that way — its
`hiltViewModelKeys` is a `Map<Class<?>, Boolean>` keyed by class literals, which R8 rewrites along
with the classes they name. Nothing reads a view model's name, so nothing needs it kept, and the
rule was costing every view model in the app its obfuscation for a lookup that no longer exists.

Two more were removed because they were inert, and they are the reason the verifier exists:

- `-keepclassmembers class com.kojo.boilerplate.navigation.** { *; }` — a package this repository
  has never had. The destinations are in `com.kojo.boilerplate.core.navigation`.
- `-keepclasseswithmembers class **$$serializer { CREATOR <fields>; }` — `CREATOR` is
  `Parcelable`'s. A generated serializer has no such field, so the rule matched nothing.

Both were in place for the life of the file, both looked like protection, and nothing anywhere
said otherwise.

## Where R8 runs

`./gradlew :app:assembleMinified`, and nowhere else.

R8 only runs on a shrunk variant, and until now the only shrunk variant was `release` — which this
repository deliberately cannot build. `:data` fails `compileReleaseKotlin` while
`gradle/certificate-pins.properties` and `gradle/play-integrity.properties` declare nothing, and
they declare nothing because the values would have to name a real server's keys and a real Play
Console project. Both gates are right. Together they meant `app/proguard-rules.pro` was a file no
build in this repository read, which is exactly how it came to hold two rules that matched
nothing. Putting placeholder pins into CI to get past that would defeat the gate whose whole
purpose is that nobody can drift past it.

So `app/build.gradle.kts` declares a third build type:

```kotlin
create("minified") {
    initWith(getByName("release"))
    matchingFallbacks.add("debug")
    signingConfig = signingConfigs.getByName("debug")
}
```

`initWith(release)` rather than a second copy of the shrinker settings — a rule verified against
one configuration and absent from the shipped one is worse than no verification. `matchingFallbacks`
is the load-bearing line: the fifteen library modules have `debug` and `release` variants and it is
`release` that cannot be built, so this variant consumes their `debug` halves. That is also why
the CI job that builds it is the one that already ran `assembleDebug` — the library outputs are
the same, and R8 is the only new work.

Debug signing, so the result is installable and a `retrace`d frame can be checked against the
device by hand. It is not the build that goes to Play: that is `release`, signed with the upload
key, once the pins and the cloud project are filled in.

## The check

`scripts/verify-r8-mapping.py` reads `app/build/outputs/mapping/minified/` and gates on what R8
did:

1. The mapping file parses, and any line in class or member position it cannot classify fails the
   run. An audit whose parser skipped half the file reports "nothing to report".
2. At least one of the app's own classes was renamed — otherwise the variant is not minifying and
   every check below would pass against an unshrunk mapping.
3. Every `@Serializable` type the app declares, and every message class the `.proto` generates,
   survived — unless `config/r8/shrunk-away-allowlist.txt` says why it could not. Both sets are
   read out of the sources, not listed in the script, because a list stops covering the type
   somebody adds next month.
4. Nothing that is looked up by name was renamed: `INSTANCE`, `serializer`, `Companion`, and
   protobuf's trailing-underscore fields.
5. `missing_rules.txt` is empty. Anything in it is a reference R8 could not resolve.

What it cannot see is a *member* being removed, unless R8 wrote a `seeds.txt` or a `usage.txt`
beside the mapping — the mapping lists what came out, and a stripped field is absent, which is
also what an identity mapping looks like. When either file is there it is used and the check is
exact; the run prints which of them it had, so the reach of the gate is in the log rather than
assumed.

`scripts/verify-r8-mapping.test.py` drives the script against fabricated mapping files to show
each check failing when it should and only when it should, including the line shapes a real
mapping holds. It needs nothing but Python, which is what keeps the gate's logic checkable in an
environment where R8 cannot run at all.

### The allowlist

A class can fail check 3 for a reason that is nothing to do with a keep rule: it is unreachable,
and R8 is right to remove it. `config/r8/shrunk-away-allowlist.txt` is where that is recorded, one
class per line with the reason, and the parser rejects an entry that does not give one.

It is checked in both directions, so it cannot outlive what it records. An entry naming a class
that *is* in the shrunk output is stale — the class became reachable and the waived check applies
again. An entry naming a class the gate never asks about covers nothing, and is usually a type
that was deleted or renamed while its exemption stayed behind.

## What the first shrunk build found

R8 had never run on this repository before the build type above existed, and its first run
reported three classes gone that the sources say should be there. All three are correct removals,
and each is a fact about the app that nothing else was going to surface:

- **`LoginRequest`** — nothing calls `AuthApi.login`. The type is named in that method's
  signature and nowhere else, so R8 removes the endpoint and its body together. Retrofit's rules
  do not hold it up: they keep the *interface* and explicitly allow its unused methods to be
  shrunk.
- **`UserPreferencesProto` and `SyncPreferencesProto`** — nothing injects
  `UserPreferencesDataSource`, so the entire Proto DataStore chain is unreachable: the Hilt
  module, the serializer, the data source and both generated messages. Which also means the
  `GeneratedMessageLite` rule above currently protects nothing, and will start mattering on the
  day a screen or a worker reads a typed preference.

Wiring either of them up is a change to the app rather than to its shrinker, so neither is done
here. Both are in the allowlist with that reasoning, and both entries fail the build the moment
they stop being true.

## Reading a crash report

The mapping is uploaded by CI as the `r8-mapping-minified` artifact with 90-day retention — a
crash arrives weeks after a build, and a mapping that expired is a stack trace nobody can read.

```bash
retrace app/build/outputs/mapping/minified/mapping.txt obfuscated-stacktrace.txt
```

`retrace` ships with the Android SDK's command-line tools. R8's own `retrace` binary takes the
same arguments and understands the compression R8 8.x writes into the mapping's header comments.

One mapping belongs to exactly one build. Two builds of the same commit produce different
mappings, so a stack trace retraced against the wrong one is not wrong in a way anybody notices:
the frames resolve, to the wrong methods.

## Not done

- **No release mapping goes anywhere.** Play Console deobfuscates crashes from the mapping
  uploaded with the bundle, and that upload belongs with the signing configuration — the next item
  in SPEC.md Phase 11. This one produces and keeps a mapping; it does not ship one.
- **`isShrinkResources` is off.** Resource shrinking is a separate decision with its own failure
  mode (a resource reached only by name), and turning it on without a `keep.xml` and something
  that exercises the screens would be a change nothing here could check.
- **Nothing has been run on a device.** Every claim above about what a keep rule prevents is
  reasoned from the library's own code or its issue tracker, and checked against the shrunk
  output. An instrumented run of the shrunk build — Phase 12's emulator matrix — is what would
  turn that into evidence.
